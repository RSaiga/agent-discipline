# security — 安全の観点 / Security lens

変更を、下の汎用の項目と、プロジェクトが足した項目（`profile.md` の `lenses.security.catalog`。無くてよい）に照らして読み、
攻撃や誤用で破れる箇所を指摘する。構造の問題は扱わない（structure の観点の仕事）。
Read the change against the generic items below and the project's additions, and point out what an attacker or misuse can break.

## 項目 / Items

番号は指摘の根拠に使う。プロジェクトの項目があれば、それを先に疑う。 / Cite the id; suspect the project's items first.

| 番号 | 項目 | 疑うところ |
|---|---|---|
| SEC-1 | 認可 | 操作する主体が、その資源に触れてよいかを確かめているか。ID を受け取って読む・書く処理 |
| SEC-2 | テナント分離 | 別のテナント（組織・ユーザー）のデータに届く経路。絞り込みの条件の抜け、キャッシュのキー |
| SEC-3 | 入力の境界 | 外から来た値の型・長さ・形式・範囲を、使う前に確かめているか |
| SEC-4 | エラーで内部を漏らさない | 応答やログに、スタック・SQL・パス・内部の識別子・依存先の生のメッセージが出ないか |
| SEC-5 | 秘密情報 | 鍵・トークン・パスワードが、コード・ログ・応答・リポジトリに出ないか |
| SEC-6 | 組み立ての注入 | 外からの値で SQL・シェルのコマンド・パス・テンプレートを組み立てていないか（文字列の連結・補間） |
| SEC-7 | 外からの呼び出しの検証 | Webhook などの署名・送り主を確かめているか。確かめる前に処理していないか |

## 読み方 / How to read

- **変更そのものは差分から読む。** 対象と差分は呼び出しが渡す（`review.md`）。追跡外の新しいファイルも対象。
- **外からの値の流れをたどる。** 入口（ルート、ハンドラ、メッセージの受け口）から、使われる場所（クエリ、コマンド、応答）まで。
  たどるのに要るだけ検索してよい（structure の観点の往復の上限は当てはめない）。ただし検索は、確かめたいことを洗い出してからまとめて出す。
- **確かめずに判断しない。** 「どこかで検証している」と見なすなら、その場所を実際に見る。

## 判定 / How to judge

- **確信度「高」には、破れる具体的な入力と、そのときに起きることを書く。** 書けなければ「中」か「低」にする。
  例: `?q=' OR '1'='1` → すべての行が返る。
- **「高」は、外の誰かが得をするときだけ。** 他人のデータに届く、内部が漏れる、権限を越える、注入できる、サービスを止められる。
  害が呼び出した本人に留まるもの（入力の誤りが 400 でなく 500 になる、など）は、破れる入力が書けても「中」か「低」。
  High only when someone outside gains: another's data, internals leaked, privilege crossed, injection, denial of service.
- **フレームワークや言語が防いでいるなら、指摘しない。** 防いでいる場所（プレースホルダ、エスケープ、型）を確かめたうえで。
- **出典の無い要件を作らない。** 言語パックの例は直し方の見本で、このプロジェクトの要件ではない。
- **誤検出を出さない。** 指摘の数より、指摘の正しさを優先する。

## 指摘の形 / Finding format

```
### [SEC-<番号> <項目>] — <file>:<line>  (確信度: 高/中/低)
- 何が問題か: <1〜2 行>
- 破れる入力: <高のときは必須。入力 → 起きること>
- 提案する手当て: <具体的に>
```

最後の行は `## LENS CLEAN` か `## LENS FINDINGS <件数>`（`discipline.md`「観点の約束」）。
