# accept — 外側のループの 1 手 / One step of the outer loop

実装のコードは書かない。書いてよいのは、受け入れテスト（シナリオ・step・その補助）とリストだけ。
Write no application code — only acceptance tests (scenario, steps, helpers) and the list.

リストの状態で、やることが 1 つに決まる / The list's state picks exactly one action:

| 状態 | やること |
|---|---|
| リストが無い | 報告して `ad-plan` を案内し、止まる |
| `## 受け入れシナリオ` の節が無い（単層） | 外側を持たない。報告して `ad-red` を案内し、止まる |
| `tdd.acceptance` が `none` | 外側を走らせる手段が無い。報告して止まる |
| `[~]` のシナリオが無く、`[ ]` のシナリオが残っている | **A. 外側を書いて落とす** |
| `[~]` のシナリオがあり、その内側に `[ ]` か `[~]` が残っている | 何も走らせない。残りを報告して `ad-red` を案内し、止まる |
| `[~]` のシナリオがあり、内側がすべて `[x]`（最初の通り道は内側を持たないので常にここ） | **B. 外側を走らせる** |
| すべてのシナリオが `[x]` で、内側に `[ ]` が無い | **C. 完了**（下） |

## A. 外側を書いて落とす / Write the scenario and watch it fail

1. **出典を確かめる。** リストのシナリオの出典を開き、承認された Given / When / Then と文言を確かめる。食い違えば、書かずに止まる。
2. **シナリオを書く。** `tdd.acceptance` の置き場所に、進行中のタグを付けて書く（既存のファイルがあれば足す）。step と補助は既存のものを使い、無いものだけ足す。
   **step の中で期待値を決めない**（期待値はシナリオに書いた値）。アプリのコードは書かない。
   - `[change]` のシナリオ: 既存のシナリオを新しい仕様に書き換え、タグを付ける。古い振る舞いのままなので落ちるのが正しい赤。
   - `[remove]` のシナリオ: 既存のシナリオと、ほかで使われなくなった step を消す。落とすものは無いので 3・4 を飛ばし、同じファイルの残りが緑であることを確かめる。
3. **スタックを用意し、そのシナリオ 1 本を走らせる**（`tdd.md`「スタック」、`run_one`）。選ばれた件数が 1 以上であることを確かめる。
4. **正しい赤か確かめる。** 正しい赤は、**アプリの振る舞いで落ちている**こと（応答が違う、要素が無い、保存されない）。
   step が未定義、構文の誤り、準備やログインの失敗、0 件が選ばれた、は赤ではない。受け入れテストの側を直して走らせ直す。
   `failure_artifacts` があれば、先にそれを見る。
   A valid red fails on application behaviour; undefined steps, setup failures and zero selected scenarios are not red.
   **最初から通ったら（最初の通り道を除く）:** 最初の通り道などの固定値がたまたまこの例を満たしているなら（その場所を file:line で示せるなら）、
   赤を見ずに通ったことと場所をリストのシナリオの下に書き、`[~]` にして、リストの内側の項目（一般化させるもの）から始める。
   内側の項目が無い・場所を示せないなら止まる。 / If it passes only because an earlier fixed value happens to fit, record where, mark `[~]`, start from its inner items.
5. **シナリオを `[~]` にする。**
   - 最初の通り道（`[skeleton]`）なら、内側の項目は作らない。この赤が green の対象になる。
   - それ以外なら、失敗が示す足りない振る舞いを確かめる（下の「失敗の読み方」）。リストに見込みの項目があればそれを先頭にし、無ければ 1 件だけ足す。
6. **止まる。** 落ちた箇所を報告する。次は、最初の通り道なら `ad-green`、それ以外なら `ad-red`。スタックは動かしたままでよい（報告に書く）。

## B. 外側を走らせる / Run the scenario

0. `[remove]` のシナリオは走らせるものが無い。内側の `[remove]` がすべて `[x]` なら `[x]` にして止まる。
1. **スタックを用意する。** 内側で変えたものがあれば、`restart_when` のとおりに再起動し、`migrate` を当てる。そのシナリオ 1 本を走らせ、選ばれた件数を確かめる。
2. **赤なら:**
   - 最初の通り道なら、項目は足さない。まだつながっていない層を報告し、`ad-green` を案内して止まる。
   - それ以外なら、足りない振る舞いを**内側に 1 件だけ**足す。そのシナリオの内側の末尾に置き、出典は「シナリオ A<n> の失敗」。報告して `ad-red` を案内し、止まる。
   - 失敗が、どのシナリオにも無い振る舞いを求めているなら、足さずに報告して止まる（ユーザーが決める）。
3. **緑なら:**
   0. **受け入れの観点をかける**（下の「受け入れの観点」）。最初の通り道と `[remove]` には、ここではかけない。
      `FINDINGS` なら、タグを外さず `[~]` のまま、破れた約束を**内側に 1 件だけ**足し（出典は「A<n> の受け入れの観点」と、破れる入力）、
      ほかの指摘は報告に全部書いて、`ad-red` を案内して止まる。`STOPPED` なら理由を報告して止まる。`CLEAN`・`UNVERIFIED` なら続ける。
   1. 進行中のタグを外す。
   2. 既定の実行（`run_default`）で走らせ、**このシナリオが選ばれて通る**こと（件数が増えていること）を確かめる。
   3. シナリオを `[x]` にする。
   4. 報告し、`ad-refactor outer`（外側の棚卸し）を案内して止まる。残りのシナリオが無ければ、自分が起動したスタックを止める。
   Green: drop the tag, confirm the default run selects and passes it, mark `[x]`, point at the outer inventory.

## C. 完了 / Done

1. **範囲を `リスト全体` にして、受け入れの観点をかける**（`acceptance` が `lenses` にあるとき）。最初の通り道で固定値のまま残ったものや、
   どのシナリオも確かめていない出典の約束を、ここで拾う。記録はリストの冒頭（完了条件の下）に書く。
   `FINDINGS` なら、破れた約束をいちばん近いシナリオの内側に 1 件だけ足してそのシナリオを `[~]` に戻し（`[skeleton]` の印があれば外す。
   もう全部の層がつながっているので、ふつうのシナリオとして扱う）、ほかの指摘は報告に全部書いて、`ad-red` を案内して止まる。
   どのシナリオにも当たらない約束なら、足さずに報告して止まる（ユーザーが決める）。
2. 自分が起動したスタックを止め、「完了」と報告して止まる。

## 受け入れの観点 / The acceptance lens

`config.yaml` の `lenses` に `acceptance` があるときだけ行う。書き手の結論を渡さないために、**新しい文脈で**起動する（同じ文脈では行わない）。
Run only when `acceptance` is in `lenses`, always in a fresh context, never inline.

1. **渡すものを集める。** 範囲（B なら `シナリオ`、C なら `リスト全体`）、シナリオの文、その出典の文（リストの冒頭の出典と、シナリオの出典）、土台のコミット（`diff_base` との分岐点）、
   変わったファイルの一覧（`git diff --name-only <土台>` と追跡外のファイル）、`tdd.rules` があればその場所。**リストの残り・自分の報告・考えは渡さない。**
2. **起動する。** `config.yaml` の `runner` が `command` なら `runner_command` で（`review.md` の `command` と同じ渡し方。中身は 1 の入力）。
   そうでなければ、ツールに `ad-acceptance` の担当があればそれを、無ければ新しい文脈の担当を使い、キットの `lenses/acceptance.md` の絶対パスと 1 の入力だけを渡す。
   新しい文脈を起動できなければ、そう伝えて止まる（`lenses` から `acceptance` を外せば、観点なしで進められる）。観点が返るまで、何も書かない。
3. **記録する。** シナリオの見出しの下に `    受け入れの観点: <n> 回目 — <最後の行>` を書く（あれば書き換える）。
4. **回数。** 1 つのシナリオにかけるのは、最初の 1 回と、直したあとの確かめ 2 回まで。3 回目でも `FINDINGS` なら、止まって報告する。
   最後の行が無い・形が違う返事は、観点が動かなかったものとして止まる。

## 失敗の読み方 / Reading the failure

最初の通り道のあとは全部の層がつながっているので、外側の失敗は「層が無い」ではなく、**つながった経路の上でどの振る舞いが足りないか**を示す。
- 項目は振る舞いで書き、それを最も直接に確かめられる境界（`tdd.tests` の種類）に置く。層ごとに割らない。
- 1 件だけ足す。先回りして並べない。

## 止まる条件 / Stop and report

- 出典が開けない・承認された文言と食い違う。
- スタックが用意できない（準備ができない、ポートが他のプロセスに使われている）。データの残りを疑うのに切り分けられない。
- 走らせ方が対象を選べない（0 件）。
- 失敗が、どのシナリオにも無い新しい振る舞いを求めている。
- 受け入れの観点が起動できない・`STOPPED`・形の違う返事・3 回目でも `FINDINGS`。

**しないこと / Never:** アプリのコードを書くこと、タグを付けずに赤のシナリオを置くこと、step 未定義や準備の失敗や 0 件を赤とみなすこと、
1 回で内側の項目を 2 件以上足すこと、最初の通り道に内側の項目を足すこと、緑になる前にタグを外すこと、自分のものでないプロセスを止めること。
